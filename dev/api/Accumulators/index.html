Accumulators

The foundation (universal lower half): the AbstractAccumulator supertype, the merge! mergeable-monoid interface, and the backend-agnostic accumulation primitive observe!.

GBGStreamingStatistics.Accumulators.AbstractAccumulator — Type
AbstractAccumulator

Supertype of every mergeable summary $T(\hat\mu_n)$ of the empirical measure $\hat\mu_n = \frac1n \sum_{i=1}^{n} \delta_{X_i}$ of an observed stream $X_1, X_2, \dots$ ($\delta_x$ the unit point mass at $x$, $n$ the number of samples seen).

A summary is finite-dimensional — the $n$ point masses are never stored — mergeable (an additive monoid over the stream; see merge!), and rich enough that every reported estimator is recoverable from it post hoc, with no second pass over the data. The summary is accumulated online and is response-agnostic; all smoothing (kernel, bandwidth, channel) is applied post hoc. Concrete carriers (Histogram1D, Histogram2D) subtype this.

Base.merge! — Method
merge!(into::AbstractAccumulator, from::AbstractAccumulator) -> into

Combine two summaries into into, forming the summary of the concatenated stream — the monoid operation that makes accumulation additive: $T(\hat\mu_{A \cup B}) = T(\hat\mu_A) \oplus T(\hat\mu_B)$. Counts add; the per-bin central moments combine by the Pébay parallel-merge formula (of which the single-sample observe! update is the $n_B = 1$ case, so the two agree exactly). This is what makes multi-device reduction and time-chunk stitching free, and lets the hot loop privatize (per-block local histograms, merged hierarchically).

merge! is intrinsically a finite-sample operation, so it has no population estimand; its specification is the monoid law, tested as accumulate-then-merge = accumulate-together (to round-off). Extends Base.merge!.

GBGStreamingStatistics.Accumulators._merge_moment! — Method
_merge_moment!(means_d, moments_d, bd, nA, means_s, moments_s, bs, nB, order)

Merge source bin bs (count nB) into destination bin bd (count nA) by the Pébay parallel-merge formula, updating means_d[bd] and moments_d[2..order, bd] in place to represent the union (the caller updates the count). moments_s is read-only, so the same source may be merged into many destinations (used by the global-moment reduction with bd = 1).

GBGStreamingStatistics.Accumulators._observe_moment! — Method
_observe_moment!(means, moments, b, n0, x, order)

Fold the value x into bin b, given the bin's prior count n0. Updates means[b] and moments[2..order, b] in place (the caller then increments the count). This is the $n_B = 1$ case of _merge_moment!, so streaming accumulation and merge! produce identical moments.

GBGStreamingStatistics.Accumulators.observe! — Function
observe!(summary::AbstractAccumulator, batch) -> summary

Fold a batch of samples into summary in place, advancing the accumulated summary $T(\hat\mu_n)$ of the empirical measure (see AbstractAccumulator). Accumulation is response-agnostic: it knows nothing of bandwidth, kernel, or which estimator will later be asked for — the architectural invariant that delivers no reruns.

Allocation-free on a preallocated summary (required for GPU hot loops, where a per-call device temporary escapes the host GC and wedges the run). Per-bin central moments are accumulated by the Pébay (2008) recursion in Float64 regardless of input element type — accumulate wider than the data (docs/ARCHITECTURE.md §3). The scatter-add binning is a serial CPU loop here; the GPU-resident KernelAbstractions + Atomix kernel (per-block privatization, merged via the monoid) and Kahan–Neumaier compensation for the very-large-$n$ regime are forthcoming (CLAUDE.md roadmap).

Reference: P. Pébay (2008), Formulas for robust, one-pass parallel computation of covariances and arbitrary-order statistical moments, Sandia Report SAND2008-6212.
