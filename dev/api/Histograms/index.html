Histograms

The summary types: Histogram1D and Histogram2D — finely binned empirical measures that fold the stream into a fixed-size form — plus observe_pairs! for two-time statistics.

Summaries

GBGStreamingStatistics.Histograms.Histogram1D — Type
Histogram1D <: AbstractAccumulator
Histogram1D(lower, upper, nbins; order = 4, accumulator_type = Float64,
            count_type = UInt64)

A finely binned empirical measure of a scalar variate $X$ — the canonical summary $T(n\mathbb{P}_n)$. The nbins equal-width bins (WARPing — weighted averaging of rounded points) tile the half-open range $[\texttt{lower}, \texttt{upper})$; choosing the range to cover the data (e.g. $\pm 5\sigma_X$ for the data's standard deviation $\sigma_X$) with $\gtrsim 10^3$ bins makes the bin width $\Delta \approx \sigma_X/100$ far below any post-hoc smoothing bandwidth $h$ ($\Delta \ll h$), so the summary is approximately sufficient.

Each bin $j$ carries its count and the power-sums $S_p^{(j)} = \sum_{i \in \text{bin } j}(X_i - c_j)^p$ about the fixed bin center $c_j$, for $p = 1 \dots \texttt{order}$. Because $X_i - c_j$ is small within a bin these are well-conditioned, so accumulation is a plain atomic scatter-add (observe!) that runs identically on CPU and GPU, and merge! is elementwise addition. The power-sums use the actual $X_i$ (not the center), so the global central moments recovered post hoc (by the shift formula — the binomial re-centering from the bin center to the sample mean) are exact, and stable for the even orders (the odd orders, $\approx 0$, keep weaker relative precision). The default order = 4 recovers the central moments up to $\hat\mu_4$; an even higher moment such as $\hat\mu_6$ needs order = 6.

Counts are UInt64 by default (summaries add) and power-sums are accumulated in accumulator_type (Float64 by default) regardless of the input element type — accumulate wider than the data. Set count_type = Float64 for the Float-count variant that scale! and weighted merge! require — the convex cone (summaries add and scale) that post-hoc re-weighting of a family of summaries (hyperstatistics) and down-weighting old data (exponential forgetting) need (a fractional weighted count is not an integer).

Samples outside $[\texttt{lower}, \texttt{upper})$ are skipped (not counted).

Arguments

  • lower, upper — the edges of the half-open range $[\texttt{lower}, \texttt{upper})$ (upper > lower).
  • nbins — the number of equal-width bins.
  • order — the highest power-sum order stored per bin (default 4, recovering up to $\hat\mu_4$).
  • accumulator_type — the element type the power-sums are accumulated in (default Float64).
  • count_type — the element type of the counts: UInt64 (the default) or Float64 for the Float-count variant.

A freshly constructed summary is empty: counts and powersums are all zeros (the merge! identity), and you observe! data into it; merge! adds counts and powersums elementwise, so same-binning summaries combine by adding these two arrays. The recovered moments are read out with central_moment and, for the first two, the Statistics extensions mean, var, and std.

julia> summary = Histogram1D(-5.0, 5.0, 1000);       # 1000 bins over [-5, 5)

julia> observe!(summary, [0.3, -1.2, 0.3, 2.1]);     # fold in a stream, never stored

julia> Int(sum(summary.counts))                      # the four in-range samples counted
4

Fields

The fields hold the summary's whole internal state, distinct from the constructor arguments (scale is derived, counts and powersums allocated); each is reachable by dot (summary.lower, summary.scale, summary.counts, …), for serialization, inspection, or building one by hand:

  • lower, upper — the range edges (upper > lower).
  • scale — the precomputed binning factor nbins / (upper - lower), stored (not recomputed) so that the binning map is a single multiply.
  • counts — per-bin counts, length nbins (UInt64, or count_type; nbins == length(counts)).
  • powersums — per-bin power-sums, $\texttt{order} \times \texttt{nbins}$ (row $p$ is $S_p$; order == size(powersums, 1)).

GBGStreamingStatistics.Histograms.Histogram2D — Type
Histogram2D <: AbstractAccumulator
Histogram2D(xlower, xupper, nx, ylower, yupper, ny; lag = 0,
            accumulator_type = Float64, count_type = UInt64)

A joint binned empirical measure of $(X, Y)$ — one per lag $\tau$ — for conditional and two-time transition densities. Its $\texttt{nx} \times \texttt{ny}$ equal-width cells tile $[\texttt{xlower}, \texttt{xupper}) \times [\texttt{ylower}, \texttt{yupper})$; each cell (ix, iy) (flattened ix + (iy-1)*nx) carries its count and the order-2 bivariate power-sums $S_{pp'} = \sum_{(X,Y)\in\text{cell}} (X - c^x)^p (Y - c^y)^{p'}$ about the cell center $(c^x, c^y)$ — $S_{10}, S_{01}, S_{20}, S_{11}, S_{02}$ — the local sufficient statistic for the joint density and for local-linear conditioning.

For a two-time quantity, the value $X(t)$ and the later response $Y(t+\tau)$ of one source (a stream trajectory) are paired; the lag $\tau$ is an explicit label on the summary. Pairs outside the box are skipped. Accumulation (atomic scatter), merge! by addition, Float64 accumulation and the count_type = Float64 Float-count / cone variant (for scale! and weighted merge!) are as for Histogram1D.

Arguments

  • xlower, xupper, ylower, yupper — the edges of the box $[\texttt{xlower}, \texttt{xupper}) \times [\texttt{ylower}, \texttt{yupper})$.
  • nx, ny — the numbers of equal-width cells in $x$ and in $y$.
  • lag — the lag $\tau$ the pairs are formed at (default 0, the static joint).
  • accumulator_type — the element type the power-sums are accumulated in (default Float64).
  • count_type — the element type of the counts: UInt64 (the default) or Float64 for the Float-count variant.

A freshly constructed summary is empty (counts, powersums all zeros), and merge! adds counts and powersums (requires matching box, cell counts, and lag).

julia> joint = Histogram2D(-5.0, 5.0, 100, -5.0, 5.0, 100);   # 100×100 cells over the box

julia> observe_pairs!(joint, [0.3, -1.2], [0.5, 0.4]);        # (X, Y) pairs, paired per source

julia> Int(sum(joint.counts))                                 # the two in-box pairs counted
2

Fields

The fields hold the summary's whole internal state, distinct from the constructor arguments (xscale/yscale derived, counts and powersums allocated); each is reachable by dot (summary.xlower, summary.xscale, summary.lag, …):

  • xlower, xupper, ylower, yupper, nx, ny — the box and cell counts.
  • xscale, yscale — the precomputed binning factors nx/(xupper-xlower), ny/(yupper-ylower), stored.
  • lag — the lag $\tau$ this joint summary is accumulated at (0 for the static joint).
  • counts — per-cell counts, length nx*ny (cell (ix, iy) at ix + (iy-1)*nx; UInt64, or count_type).
  • powersums — $5 \times (\texttt{nx} \cdot \texttt{ny})$: rows $S_{10}, S_{01}, S_{20}, S_{11}, S_{02}$ about the cell center.

Accumulation

The verbs observe! / merge! are the universal Accumulators interface; observe_pairs! folds two-time pairs into a Histogram2D.

GBGStreamingStatistics.Histograms.observe_pairs! — Function
observe_pairs!(summary::Histogram2D, x_past, y_now) -> summary

Fold a batch of pre-formed pairs $\bigl(X(t), Y(t+\tau)\bigr)$ into the per-lag summary in place (x_past holds $X(t)$, y_now holds $Y(t+\tau)$, equal length) — the entry point that stores no sample. The pairs are binned by an atomic scatter-add (one work-item per pair, CPU or GPU); everything that produces the pairs — the buffer of past $X(t)$ snapshots, which sources (stream trajectories) to sample, which lags to form, how often to start a pair — is the consumer's (the calling code's) responsibility, formed at the summary's lag $\tau$.

Arguments

  • summary — the per-lag joint Histogram2D the pairs are folded into.
  • x_past — the conditioning values $X(t)$, one per pair.
  • y_now — the response values $Y(t+\tau)$, one per pair, in the same order as x_past.

Persistence (HDF5)

With the HDF5 package loaded, a summary reads from and writes to an HDF5 group of a file you open and own — so it sits beside your other datasets, one file with many groups. This is provided by a package extension, which keeps HDF5 out of the core dependency tree. Write with write_histogram (or the equivalent parent[name] = summary sugar); read with read_histogram. The reload is exact and still merges.

GBGStreamingStatistics.Histograms.write_histogram — Function
write_histogram(parent, name, summary)

Persist a Histogram1D or Histogram2D summary as a new HDF5 group name under parent (an open HDF5 File or Group), returning that group. The summary is the durable artifact of the streaming design — a fixed-size object — so this is how you checkpoint it, resume from it, or combine summaries stored across runs; the reload is exact.

The group is self-describing: the arrays become datasets (counts, powersums) and the scalar parameters become attributes (type, version, the range edges, nbins / nx / ny, order, lag), so any HDF5 tool can read it. Device (GPU) arrays are copied to the host on write, and the count element type is preserved, so the count_type = Float64 cone variant round-trips. The sugar parent[name] = summary is equivalent.

The handle parent is one you opened and own — this never opens or closes a file. A package extension provides this method; it is available only when HDF5 is loaded.

Arguments

  • parent — an open HDF5 File or Group to create the new subgroup under.
  • name — the name of the group to create.
  • summary — the Histogram1D or Histogram2D to write.

GBGStreamingStatistics.Histograms.read_histogram — Function
read_histogram(parent, name)

Reconstruct the summary written by write_histogram from the HDF5 group name under parent (an open HDF5 File or Group), dispatching on the stored type attribute to return a Histogram1D or a Histogram2D. The reload is exact — counts, power-sums, range, element types, and (for a Histogram2D) the lag are recovered bit-for-bit, and the result merge!s with other summaries of the same shape.

The reconstructed summary is a host (CPU) object regardless of where the written one lived; move it to a device afterward if needed. A package extension provides this method; it is available only when HDF5 is loaded.

The arguments are parent, an open HDF5 File or Group holding the group, and name, the name (or path) of the histogram group under parent.
